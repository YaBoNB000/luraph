## R008 复盘：㉒ 是怎么被破的

㉒ 消灭了「解码态原型表常驻内存」，但留下了一个更便宜的口子：

- **可见 boot 里存在解码态落地窗口**。引导链中 `MPF = ENC(PF, ...)` 之前，
  解析结果 `PF`（全部解码态指令流+常量池）是一个**可见层局部变量**——
  Nop 自改写（`PF[i].W[p] = NOPA`）与 ENC 调用都在可见代码里触碰它。
- 攻击因此**不需要任何动态能力**：对可见文本做手术，在解码赋值之后插入
  一段序列化转储，即拿到全程序明文（我方自攻复现：单点插入，1422 条
  键值全量转储，程序照常运行）；或者干脆两处文本编辑把 ㉒ 整个禁用。
- 结论：**只要解码态在可见层出现过一次，「即用即毁」就名存实亡**——
  内存侧防护对文本手术无效。

## 增量㉓ 的修复：解码窗口整体入密

- **BSS 碎片（解析器，本身就是加密碎片）合体**：解析 → 校验 → Nop 自改写
  → 原型重编码 → 链原型树，全部在同一个 loadstring 出的加密碎片内一步
  完成；它**只把编码态树根递回可见层**。
- 可见 boot 从此只有密文交接：`MPF = LS(BSS)()(...)(FN, NOPA, 钥匙×4)`，
  解码态原型表**从未在可见代码中存在过**。
- 代价（诚实披露）：可见侧失去 Nop 自改写的直写形态（F14/F27 的 ZW 形状
  挪进碎片，轮廓 32/32 仍全过——其余可见写形态足以撑住口径）。
- 攻击者现在要拿解码态，必须先完整破译引导链（碎片钥匙 → HBOOT → HQ
  循环 → BSS 碎片 → 碎片内移植解析器+编码器），**每构建全部重建**；
  文本手术无目标可插。
