# 红队侦察报告：真实 Luraph v15 样本静态逆向（`main:luraph15.txt`）

> 2026-09-07 · 选项B 收官配套侦察。目标：以攻击者身份静态逆向真实
> Luraph v15 样本（171,753 B），找出「我们应对不来」的防御并评估是否
> 学进本产品。**结论先行：真实 v15 没有任何运行时防御，纯结构混淆；
> 其全部解码机制都是文件内确定性变换、无文件外秘密。本产品在每个可
> 度量轴上已持平或领先，无需引入其任何机制。**

---

## 0. 方法与纪律

- 纯静态：不执行样本、不 `loadstring`、不运行任何解出的代码。
- 自建 Python 工具：长字符串/块平衡词法器（处理 Luau if-表达式 `=if..then..else`
  无 `end` 的块计数陷阱）、模块表字段枚举、载体拼接还原、LCG/转义模拟。
- 所有定位给字节偏移与精确表达式，可复核。

## 1. 样本身份

- `main:luraph15.txt`，171,753 B，头部 `-- This file was protected using
  Luraph Obfuscator v15.0 [https://lura.ph/]`。
- 结构 = `return setmetatable({...227 字段...},{}):FC()(...)`（与我们 v15
  profile 克隆的外壳同构）。

## 2. 模块表测绘（227 字段 = 154 命名 + 73 数字槽）

- **73 个数字槽 = 原语表**（与我们 P2 原语槽同构）：`[66]=buffer.readu8`、
  `[47]=buffer.writeu8`、`[8]=bit32.bxor`、`[118]=string.gsub`、
  `[93]=string.sub`、`[107]=buffer.fromstring`、`[51]=buffer.create`、
  `[81]=pcall`、`[14]=xpcall`、`[34]=getfenv`、`[25]=setfenv` 等。
- **145 个函数字段**：绝大多数是 CPS 状态机微型 handler（见 §4）。
- **命名常量**（与我们 v15 模块常量同形）：`AL="n"`、`BL="__index"`、
  `QL=false`、`EL=": "`、`cL="string"`。
- **大字段**：
  - `RC` = **74,575 B** 长字符串 `[=[...]...]`，前缀 `LPH:`（品牌水印，
    明文可见，非安全机制）。
  - `[18]` = **32,695 B** 主解释器函数（**明文可见**）。
  - `[73]` = 3,366 B 闭包工厂（用 `pcall` 包裹解释器创建，纯错误处理）。
  - `Y`(4.6K)、`a`(3.3K) = 嵌套分派器（调用 `b:zL/yL/M/S/E/P` 子机）。

## 3. 载荷链与解码机制（全部文件内、确定性）

引导 handler `HL`：
```lua
local u = b[118](b[93](b.RC, 5), b.XC, b.pC)  -- gsub(sub(RC,5), "[ -'}~]", pC)
local z, Z, K = b[107](u), #u-1, 5+0           -- buffer.fromstring
return 2, {nil,0-K,K,Z+0,o}, 0, {}, z, w       -- 交给状态机 state=2
```
- `b[93](b.RC,5)` = `string.sub` 去掉 4 字节 `LPH:` 前缀。
- `b.XC = "[ -'}~]"`（10 个特殊字符：空格 `! " # $ % & ' } ~`），
  `b.pC` = 10 项「单字符→5 字符」转义表（如 `"`→`=W8+C`）。`gsub` 把
  这 10 个字符展开——**实测整个 74.5K 载荷只命中 32 处**，即这层只是
  转义保护，不动主体。等价于我们的 TK 转义表。
- 展开后 `buffer.fromstring` 得 74,690 B 缓冲，交给 CPS 机逐字节解码。

**字节级解码 = LCG(213,225) 钥匙流逐字节 `bxor`**，散布在 ~150 个微型
handler 里。例（`oL`）：
```lua
local f,B,j,d,Y,_ = 1+q, 213, 225, (Z+18)%256, b[51](4), 0
local g = (d*B+j)%256                     -- LCG 步进
b[47](Y, _, (b[8](18, b[66](K,f+_), g)))  -- writeu8(buf, i, bxor(18, readu8, g))
```
- 常数 `213`/`225` 全文出现 25/28 次，**全是明文字面量**。
- 与我们脚手架的「分块 handler + LCG 钥匙流 XOR」完全同构（我们 §⑩/⑬/⑭
  已有，且我们把它进一步入密 + 查表装配，钥匙不落明文）。

## 4. 分派模型：嵌套多机微 handler

- 控制流 = 阈值树状态机分派到 **145 个命名微 handler**，命名规律为每个
  字母三变体 `x` / `xC` / `xL`（`jC/oL/gC/NC/hL/NL/ZL/SL/GL/VL/XL/FL/IL/…`）。
- 高频交叉调用：`b:iL(`（330 次）、`b:vL(`（239 次）为编码/变长整数助手。
- 主解释器 `[18]`（32.7K）与闭包工厂 `[73]`、嵌套分派器 `Y`/`a` **全部
  明文可见**——解释器逻辑不加密，加密的只有 `RC` 字节码。

## 5. 决定性发现：真实 v15 无任何运行时防御

全文检索（含解码机制层）：

| 检查 | 真实 v15 命中 | 本产品 |
|---|---|---|
| `debug` / `debug.info` | **0** | nlok + pb 探针钥匙化（§⑯） |
| `loadstring` 原生复检 | **0** | nlok 陷阱 + S5 口径（§⑲附带） |
| `[C]` 来源判定 | **0** | pb fold（§⑯-1） |
| `newproxy` / 元方法诱饵 | **0** | 有（guard/anti） |
| 激活绑定 / 输入门 | **0** | ⑱⑳（双因子非线性） |
| 解释器加密 | **否（明文）** | 是（handler/parse/dispatch 全入密） |

真实 v15 的防御 = **纯结构混淆**（CPS 微 handler 解码 + 嵌套多机 + 字节码
加密），无一处运行时环境/完整性/输入绑定防御。

## 6. 「应对不来」的墙（诚实记录）

本次纯静态侦察**没有遇到密码学墙**——所有解码都是文件内确定性变换。
真正卡住的是**工程繁琐墙**：要把 74.5K 载荷完整还原成原型/字节码，必须
模拟 ~150 个微 handler 的 CPS 状态机、逐字节跟 LCG(213,225) 状态、穿
`b:iL/b:vL` 助手与 `x/xC/xL` 嵌套分派。这是「需要为每个构建写专用模拟器」
的成本墙，不是「文件里缺秘密」的不可解墙。**与 R006/攻击方 Q7 结论一致：
静态可解的前提是所有秘密都在文件里；本产品 ⑱ 引入文件外激活秘密后，这条
静态路径在本产品上不再成立。**

## 7. 对照结论与决策

| 轴 | 真实 v15 | 本产品 | 判定 |
|---|---|---|---|
| 解释器 | 明文可见 | 全入密 | **我方领先** |
| 解码散布 | ~150 微 handler | 分块 handler + 入密 | 我方持平偏强 |
| 载体 | base 转义 + LCG-XOR | base94 + TK + LCG + 查表钥匙 | 我方领先 |
| 运行时防御 | **无** | nlok/pb/guard/⑯⑱⑲⑳ | **我方领先** |
| 输入绑定 | **无** | ⑱⑳ | **我方领先** |
| 结构混淆 | 嵌套多机 | CPS 脚手架 + ⑲ 尾链 | 相当 |

**决策：不引入真实 v15 的任何机制。** 其唯一与我们有别的结构点是
「嵌套多机 `x/xC/xL` 分派」——属「增加分析繁琐度」的混淆，非安全增益；
本产品 ⑲ 已用「去中心化尾链」以不同（且更抗 hook）的方式覆盖了咽喉点
目标。把 bootstrap 拆成多个互调用状态机可作为**可选的未来结构加固**，但
指纹耦合高、收益不确定，暂不实施。

**本报告的真正价值**：以实证确认「真实 Luraph v15 = 纯结构混淆、无运行时
防御」，反向印证本产品「结构混淆 + 运行时防御 + 输入绑定」三层路线是对
R006 动态破解的正确投资方向——真实 v15 面对 R006 那种可控运行时攻击会
比本产品更快被还原。
