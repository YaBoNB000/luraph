## 0. 为什么单独立项

样本的执行模型与我们**本质不同**：

| 维度 | 我们现状（A1 后） | 样本 |
|---|---|---|
| 执行驱动 | 单 `while true` 分发循环（`run`） | CPS 状态机，handler 返回 `(nextId, 元组)` |
| 指令处理 | 分发树叶子内联执行 | 142 个细粒度 handler，按状态 ID 串接 |
| 帧模型 | 闭包直接调 `run` | 每帧一个新 Lua 闭包（CPS） |
| 流水线 | 解码+执行混在一个 `VM` 闭包 | 构建/校验/解码/执行分阶段独立循环 |
| fetch 循环数 | 2（F11） | 19（F11 黄金值） |

把 F11 从 2 拉到样本量级、并让执行真正变成多段状态机，**只能靠重写执行
模型**——这就是 A2b。它不是「再加几个开关」，是换一台引擎。因此单独立项、
分阶段、每阶段带回滚门。

## 2. 目标架构（映射样本概念 → 我们的实现）

```
return setmetatable({
  -- ① 数字槽：68 原语 + 2 运行器 + 常量        （已具备，增量 2/5）
  -- ② 命名字段：AL/BL/.../RC/pC/XC              （部分具备）
  -- ③ 引导状态机 FC：解码 blob → 建 SoA 原型     （A2b-阶段 B）
  -- ④ 执行状态机 L：CPS 驱动帧执行               （A2b-阶段 C/D）
  -- ⑤ 细粒度 handler 族：每指令 ≥1 个，          （A2b-阶段 D）
  --    返回 (nextId, 元组...)
}, {}):FC()(...)
```

**状态元组**：执行状态打包成位置参数元组 `(pc, V, pf, ups, vargs, lastn,
lastbase, ...)`，在 handler 间以多返回值传递（样本同款）。每构建元组槽序
洗牌（我们已有 shuffle 机制可复用）。

**CPS 循环**：`while flag do ... leaves: 元组 = b:handler(元组); continue ... end`
（我们已有 continue-leaf 骨架，增量 5 已验证可行）。

## 3. 分阶段实施（每阶段 = 独立增量 + 回滚门）

> 每阶段的**回滚门**：全量语料 + 多种子 + 矩阵 204 + 预设 405 全绿才提交；
> 任一失败 → 回滚该阶段改动，不带病推进。

### 阶段 B —— 解码流水线独立成段（中风险）✅ 完成（2026-08-28）
把 `parse(FN[i])`（载体→SoA 原型）从 `VM` 闭包里抽出，改为独立的**解码
状态机段**：① 原型级解码循环独立成段（`while di<=#FN`）；② `parse` 本体
改为**显式解码相位状态机**（`st=1..5`：头/upsrc/常量/码流/操作数流五个
相位，状态变量驱动，语义与单体版逐条等价）。产出独立的解码段结构
（CPS 流水线地基）。
- 改动：`template.rs` 解码段 + `parse` 参数化为 `{parse_fn}`（非 v15 保留
  原单体版，字节级零变化，已验证 0 变更）。
- 回滚门：全量语料 + 多种子 5×6 + 矩阵 204 + 预设 405 全绿 ✅。
- 状态：✅ 已完成。解码段与执行段已分离，均为状态机形态。

### 阶段 C —— 执行循环 CPS 化（高风险，核心）
把 `run` 的 `while true` 分发循环改为**状态机驱动的 CPS 循环**：
- 每条指令 = 一个（或几个）handler，吃 `(pc, V, ...)` 元组，吐
  `(nextId, pc', V', ...)`。
- 分发不再是树内联执行，而是「按状态 ID 调 handler」。
- 跳转指令 = 返回新 `pc` 的状态转移；`Return` = 返回到调用帧。
- 回滚门：全量回归 + 针对用例（跳转/闭包/多值/协程）。
- 风险：**高**。这是执行模型的根本改变，upvalue/多值/尾调用语义最脆弱。
  必须先有阶段 B 的稳定解码，再做执行。

> **⚠️ 阶段 C 首次尝试结论（2026-08-28，已回滚，务必先读）**
>
> 做了「每指令一个独立 handler（`H[OC.xxx]` 分派）+ `pc` 经闭包传递 +
> `Return` 经信号表返回」的语义保持 CPS 骨架。14/15 个针对语料通过，
> 但 **`functions.lua` 的 `tail(5000)` 深尾递归栈溢出**（丢 `tail-done`）。
>
> **根因（架构属性，非控制流 bug）**：CPS 把每条指令的分发变成一次
> `H[oc](a,b,c,d)` 函数调用。函数调用（`Call` 系 opcode）会递归进
> `run`，于是**每层递归比内联分发多一个 `H[Call]` 栈帧**。`tail(5000)`
> 这类深尾递归（我们的 VM 用 `lastn/lastbase` 模拟尾调用、**不做真
> TCO**，每层本就加一个 `run` 帧）再多一帧，就被顶爆。内联分发版能过
> （少那一帧），CPS 版溢出。
>
> **结论**：CPS handler 分发模型有「每调用 +1 帧」的固有栈代价，深尾
> 递归语料必然触发。要让阶段 C 落地且语料保持全绿，必须先解决栈代价，
> 两条路：
> 1. **内联 Call 系 opcode**（Call/CallE/CallM/CallT 在分发循环里直接
>    处理、不经 `H[]`）——递归不再多那一个帧。中等复杂度，但破坏「全
>    opcode 皆 handler」的纯度。
> 2. **实现真尾调用优化（帧复用）**——尾调用复用当前帧、不再叠加
>    `run` 帧，根治深尾递归栈深。这是「正确」的修法，也是真改进（内联
>    版同样受益），但属调用约定根本改动，对闭包/upvalue/多值风险最高。
>
> 本次已按回滚门**回滚 CPS 改动**，恢复内联分发，全量回归回到
> 204/204 + 405/405 全绿。**阶段 C 暂停，待选定栈代价解法（方案 1 或
> 2）后再推进。**

> **✅ 用户选定方案 ②（真尾调用优化），第一步已落地（2026-08-28）：**
>
> **真 TCO 实现**——不靠识别 VM 闭包/注册表，而是让 `makefn` 闭包对
> `run` 的调用成为**真尾调用**，由 Lua 原生 TCO 复用栈帧：
> - `Return` opcode 由 `return out, total` 改为 `return U(out, 1, total)`
>   （直接返回解包结果，`run` 返回类型随之变为「解包后的多值」）；
> - `makefn` 闭包由 `local out, n = run(...); return U(out, 1, n)` 改为
>   `return run(pf, V2, c, vargs, vargc)`（尾调用，帧被复用）；
> - 顶层调用同改尾调用。
>
> 深尾递归不再每层叠一个 `run` 帧——`tail(5000)` 实测通过（此前 CPS 版
> 溢出）。`callcap` 兼容（仍以 `{...}`+`select('#')` 捕获多值）。
> **验证**：30 语料 + 多 seed 5×8 + 矩阵 204/204 + 预设 405/405 全绿；
> 3 个 `.vm` 样本因共享 `run` 改动字节级变化（语义验证通过，属预期）。
>
> **意义**：真 TCO 让「闭包→run」不再叠帧，是内联与未来 CPS 分发共同
> 受益的地基，也是真语义改进（对齐「5.1/Luau 都做真尾调用」）。阶段 C 的
> CPS 分发将在此地基上重做；届时逐指令经 handler 是否仍叠帧、是否需再
> 内联 Call 系，在 CPS 重做时实测确认。

### 阶段 D —— 每帧一个闭包 + 帧运行器（高风险）
把「闭包直接调 `run`」改为「`makefn` 返回的闭包 = 新帧，经帧运行器
（数字槽 `[73]/[18]`）启动」。每帧一个新闭包（样本 CPS 帧模型）。
- 回滚门：闭包/协程/多值全量回归。
- 风险：高。帧边界 + upvalue 传递是雷区。

### 阶段 E —— 指纹收口
F11（多段 fetch 循环）、F12（pcall 帧包装）、F5（方法调用/状态返回量级）
随 B/C/D 自然增长；最后对照样本逐项核对 32 条指纹，补细节（7-bit 分块、
LCG 密钥流等已在增量中具备）。

## 4. 风险总览与止损

- **最大风险**：阶段 C 的执行模型改变打爆 upvalue/多值/尾调用。止损：
  阶段 C 单独一个增量，失败即回滚，不带病进 D。
- **性能**：CPS 逐指令经 handler 调用，比单循环慢（样本 ~190 万 op/s
  可作上限参考）。v15 档本就慢于非 VM，可接受。
- **确定性**：所有随机性仍走种子 `rng`；新发射器不引入新随机源即保持
  「同种子同输出」。
- **不碰非 v15 预设**：`generate` 原样保留，5.1 / 默认预设矩阵绝不回归。

### S1 密钥流状态机化（✅ 完成，消灭最高危差距）

**问题**：增量 6 的载体 XOR 用 `(K1*i+K2)%256`，K1/K2 是**明文常量**写在
每个分块 handler 里——攻击者找到一个分块 handler 即读出密钥（锁了门把
钥匙贴门上）。

**修复**（样本 `[96]` 同款）：
- 新增 **KSC 槽**（存 LCG 状态，播种）+ **KG 槽**（3 步 LCG 状态机生成器，
  常数内嵌在状态转移体里）。
- 分块 handler **不再含任何密钥常量**，运行时调 `b[KG](b)` 取本分块密钥
  常数，再 `(kv+i)%256` 解；构建期用同一套 3 步 LCG 生成密钥流做 XOR，
  往返一致（30 语料 + 多种子 5×8 验证）。
- 密钥常数只存在于 KG 状态机体内，**解码点静态不可提取**。

**验证**：30 语料 + 多种子 5×8 零失败；矩阵 204/204 + 预设 405/405 全绿；
非 v15 示例 0 变更；`268435456` 仅出现于 KG 生成器（1 处）。

**后续安全项**（按差距排序）：操作数 7-bit 分块不透明化（S2）、执行段
CPS 化抬高动态分析成本（即阶段 C，安全+结构双重收益）。
