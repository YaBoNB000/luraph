## 1. 样本再读结论（相对 `docs/luraph15-analysis.md` 的增量）

本次直接从 `origin/main:luraph15.txt` 抽的硬数字：

```
return setmetatable({ jC=function(...) ... end, ..., [51]=buffer.create }, {}):FC()(...)
```

- 入口 **不是** `loadstring`。整个脚本的值就是模块表，`:FC()` 跑引导状态机，最后返回用户入口再 `(...)`。
- 模块表同时是：opcode handler 仓库、原语别名表、常量箱（`QL=false`、`AL="n"`）、blob（`RC`）、转义表（`pC`）、字符类（`XC`）。
- 分发是 **CPS + 状态 ID**：handler 几乎都以 `return <nextId>, <元组...>` 结尾（351 次 / 136 个 ID）。静态看不到一张 opcode switch。
- 子分发器高度收敛：方法调用 `b:iL(...)` 330 次、`b:vL(...)` 239 次——这两处就是动态 hook 的收敛点。
- 数据层是 **Roblox buffer + bit32**，不是 string。`buffer.create` 是表的最后一个字段，和 handler 写在同一张表里。
- `continue` 是 Luau 形态的一等公民（45 处），用来把决策树压成扁平叶。
- **没有** `os.clock`。我们的 L7 时间陷阱会立刻让产物「看起来不像 v15」。

分析文档 §8 当时的决策（拒 buffer、拒 Vector3、CPS/超级指令延期、保留校验和/时间陷阱）在 **双目标产品** 上仍然正确，但和「看起来就是这份 v15」**直接冲突**。

### 1.1 二轮详读架构修正（2026-08-25，全文脚本复测）

此前基于分析报告的心智模型有 **5 处结构性错误**，P 阶段按下面修正：

1. **「三层分发」重新定位**：高频方法调用 `iL`（330 次）/`vL`（239 次）**不是分发器**——
   `iL`=32 位乘法（bit32.band/rshift/lshift 组合），`vL`=`%2^32` 归一。它们是
   **算术助手**，被帧运行器在解码/密钥运算中反复内联调用。真正的分发是：
   - **4 个顶层变参状态机**：`FC`（引导，3 分支→qL/HL/eL）+ `D`/`J`/`K`
     （其余变参入口），入口仅 `:FC()(...)`。
   - **阶段子机（XL 族）**：FC 的分支按 `V<=N` 范围树调子机；子机返回
     **控制码**（eL：2=继续/1=返回；L 机的 aL：1=继续/2=返回——**语义每机相反**）。
     `L` 机 8 分支（DL/JL/fL/kL/sL/aL/ML/SL），且 `L` 由 `eL` 内部调用
     （`b:L(` 全文件仅 1 处）——**阶段切换藏在分支里，不在入口**。
   - **CPS 循环 `a`**：`b:M(Z)` 初始化 14 值上下文表 → `while o` + 二叉树，
     叶 = `元组 = b:单字符handler(...); continue`（**45 个 continue 全在 `a` 一个函数里**）；
     特殊叶 `b:_(...)` 返回控制码（1=继续/2=返回）。部分调用把**上下文表 Z 整个传入**
     （`b:S(Z,R,S,Y,J,y,O)`）——元组传参与整表传参两种约定并存。
   - **141 个具名函数多数是引导/解码管线的细粒度步骤**（返回 `(nextId, 元组)`，
     351 处 / 136 个不同 ID），**不是运行期 opcode handler**。
2. **运行期执行 = 两个数字槽运行器内的内联树**：`[18]`（协程运行器：入场解包含
   `coroutine.wrap`+`UL`）与 `[73]`（普通运行器：解包含 `b.nL`+`QL=false`）。
   `[18]` 内有 ≥4 个 fetch 循环（`O=J[Q]` 主执行 + `q=J[Q]`/`q=y[Q]`/`q=R[Q]`
   多段 + 6 个捕获清理循环）；`[73]` 内 3 个（`f=m[x]`/`B=z[u]`/`o=u[z]`）。
   opcode 是小整数（19–34+），handler 体直接写在二叉树里（MOVE/GET/CALL/RETURN/
   upvalue 写 `p[4][p[7]]=n[R[Q]]`/捕获清理 `D[4]=D;D[6]=n[i];D[7]=6` 等）。
   **旧计划「把 41 条 ISA 拆成细粒度 handler」对运行期是错的**：handler 化的是
   引导管线，执行循环必须内联。
3. **帧与入口细节**：帧 = 运行器里 `l,A=0,function(...)` 造包装闭包 →
   内部 `pcall(function...)` 再包一层 → 帧内 `n=table.create(size)` 建寄存器文件、
   `local k,s,W,p,L,C,I,h` 8 个工作寄存器；入场魔数门 `S==251`。
   参数刻意遮蔽（`function(b,u,z,z,z,z,z)`）。
4. **密钥流的真相**：真实解码密钥是**内联一次式**
   `bxor(201, (213*q+225)%256, readu8(...))`（dC handler），常数每构建随机；
   `[63]`/`[96]` 的 LCG 状态机工厂**静态零调用**（`b[63]`/`b[96]` 引用为 0，
   68 次 `b[1][4][...]` 写入全在这两个函数体内）——**是诱饵**（或经计算槽动态调用）。
   模块表 `b[1]` 运行期被改写为状态表（先当 buffer.fill 用、后当 `b[1][4]` 容器）。
5. **数据层语义**：操作数块字节带 **+128 偏置**（`-128` 264 次），重建用乘加不用
   bit32；varint 是 4 级内联阶梯；SoA 数组**边跑边改**（9 处常量写回）；
   [73] 的 SoA 写回全部过随机常数 mul32 线性变换（不透明算术）；
   `h={24123,...9 个大常数}` 与 site1 死循环是**静态不可达的诱饵**。

**对 P 阶段的净影响**：P3 重写（引导管线 handler 化 + 执行循环内联化）；P5 改
「诱饵 LCG + 真实一次式密钥」双层；P6 cell 布局按 `{[4]=bank,[7]=slot}` 映射；
P7 增加自修改/偏置/不透明算术/varint 阶梯；P0 指纹脚本扩到 32 条。

## 2. 必须先拍板的分叉

100% 结构还原 **不能** 同时满足「输出长得像这份 Roblox v15」和「同一份输出在 Lua 5.1 上可跑」。

| 路线 | 目标环境 | 和样本的像 | 5.1 | 建议 |
|---|---|---|---|---|
| **A. `--preset v15`（Roblox 克隆档）** | Luau + `buffer`/`bit32`/`typeof`/`setfenv` | 可以冲 F1–F20 | 放弃（或另出 polyfill 档，但指纹会脏） | **要 100% 外观就走这条** |
| **B. 双目标结构孪生** | 5.1 + Luau，table/string 代替 buffer | F1–F8、F11–F12、F15 可像；F9/F13/F16/F19 永远不像 | 保住 | 这是旧设计；上限大约 70% 指纹 |

handler 属于**引导/解码管线**；**运行期 opcode 执行内联在两个运行器的二叉树里**，
不是 handler。旧版「把 41 条 ISA 拆成 handler」的方向要反过来。

**A. 引导管线（handler 化）**
1. 把「容器解码 → SoA 重建 → 常量/原型装配 → 入口函数生成」拆成
   **~40–60 个单字符细粒度步骤函数**：每个吃 `(self, 元组...)`，做一小步
   （读 1–4 字节 / 重建一个值 / 写一个槽），以 `return <nextId>, <元组>` 结束。
   状态 ID 池每构建随机（样本：351 处返回 / 136 个不同 ID，范围 1..236）。
2. **CPS 循环 `a`**：`while <flag>` + 二叉范围树，叶 = `元组 = b:handler(...); continue`
   （continue 叶集中在这一个函数，样本 45 处）；一个特殊叶 `b:_(...)` 返回
   控制码（1=继续循环 / 2=返回结果）。部分调用把上下文表整个传入（两种约定并存）。
3. **顶层状态机族**：入口 `:FC()` + 2–3 个额外变参机（样本 `D`/`J`/`K`）；
   每机 = `while <flag>` + 范围树（FC 3 分支、L 机 8 分支）调阶段子机（XL 族）；
   **阶段切换藏在一个分支内部**（`eL` 内调 `b:L(`，全文件仅 1 处）；
   **控制码语义每机随机反转**（FC：2=继续/1=返回；L：1=继续/2=返回）。
4. **初始化器族**：每机一个 `return true,<startId>,nil×k`（样本 4 个，
   元组宽度 10–14 各异）；入口机入场后先 `local V,f,...=z,Z,...` 重命名元组。
5. **算术助手（XL 族的另一半身份）**：生成 8–15 个纯算术小函数——
   mul32（band/rshift/lshift 组合，样本 `iL`）、mod2³²（样本 `vL`）、
   各宽度 varint 读器（`wL`/`sL` 形态，返回 `(next, pc', 值)`）——
   被运行器/解码步骤高频调用（样本 iL 330 + vL 239 次）。
6. 每构建：handler 名（按 §P2 字母表族）、分支切分、阈值、元组排列、
   控制码取值、枢纽 ID 全随机。

**B. 运行期执行（内联化）**
7. 两个数字槽运行器（普通 + 协程）内各生成 **多段内联二叉树执行循环**：
   主段 `local O=J[Q];if O>=...` 执行用户指令 + 2–3 段辅助循环（构建/校验/解码，
   其中 1 段可为死路径）+ 捕获清理循环。opcode handler 体直接写在树叶里
   （小整数 opcode 池，每构建置换）。
8. 每构建随机 **1 条永不命中的死循环**（样本 site1：`local f=m[x]` 但永不进入）。

**验收**：F5 F6 F7 F11 F12；`return <数字>,` 次数与不同 ID 数进入样本同数量级
（≥100 次 / ≥30 个 ID，不必等于 351/136）；continue 叶集中在单一函数；
算术助手调用次数 ≥100；执行循环 ≥3 段且 ≥1 段死路径。

### P4 — blob 流水线改成「看得见的 v15」（约 2 天）

现有 `Carrier`（base-94 + 保留前缀 token）语义可用，但**发射形态**必须改：

- 主程序字节码进 **一张长字符串** `RC=[=[LPH:...]=]`（或 `[==[` 避冲突），不是 L5 的 3–5 段短串。
- 表上挂 `pC`、`XC`；引导阶段 `string.sub` + `gsub(XC,pC)` + `buffer.fromstring`。
- XOR 流：`buffer.writeu8(buf, pos, bxor(K0, (K1*q+K2)%256, readu8(src, pos+G)))`
  ——**三个常数 K0/K1/K2 每构建随机**（样本 201/213/225），密钥状态 `q` 按一次式
  滚动；密钥来自 **输出里的 LCG 状态机**（P5，诱饵层），不是构建期写死的 24B。
- 解码写进 `buffer`，再拆成 SoA 平行数组（可仍是我们的 ISA）。
- **操作数块字节带 +128 偏置**（F13）：编码时 `byte+128`，解码 `(x-128)`
  乘加重建，不用 bit32（样本 `-128` 出现 264 次）。

**验收**：F8 F13 F16；打开产物能用眼睛看到 `RC=[=[LPH:` 和 `pC={`、`-128` 成片。

### P5 — 密钥双层：真实一次式 + 诱饵 LCG（约 1 天；§1.1 修正）

二轮详读发现样本的 LCG 状态机**静态零调用**（`b[63]`/`b[96]` 引用为 0），
真实密钥是内联一次式——所以指纹对齐要**两层都做**：

- **真实层**：解码/执行密钥用内联一次式 `(K1*q+K2)%256` 滚动 + `bxor(K0,...)`，
  常数每构建随机（承担真实密钥流，P4 的解码器用它）。
- **诱饵层**：再生成 2 个 LCG 工厂槽（样本 `[63]` 2 步 / `[96]` 多态展开，
  合计 ~68 次 `b[1][4][b[1][7]]` 写入、mod 2²⁸ = `%268435456`），
  形态完整但**不接线**（静态不可达）——与样本同构；配套 `b[1]` 运行期
  自变异（先当原语用、后被改写成状态表）与 `h={大常数×9}` 死表（F28）。
  我方原有 24B 嵌入密钥**取消**（输出里禁止出现连续密钥字面量）。
- 决策注记：若不想留死代码，可把诱饵 LCG 真正接成密钥源（比样本多一层
  强度），但会牺牲「静态不可达」这条指纹——**默认按样本做诱饵**，
  接线版作为 `--preset v15-hard` 预留。

**验收**：F15 F28；对产物 grep 不到长密钥，能 grep 到 `% 268435456`；
LCG 槽存在且静态无调用方。

### P6 — CPS 帧 + 双运行器 + UL（约 3 天，语义雷区）

- 用户函数调用 = 返回新闭包（新寄存器银行 + 新状态表），上层再调。
  样本帧结构：包装闭包 `l,A=0,function(...)` → 内部 `pcall(function...)` 再包
  一层（错误捕获与 `nL` 重写挂钩）→ 帧内 `table.create(size)` 建寄存器文件 +
  8 个工作局部（样本 `k,s,W,p,L,C,I,h`）；入场魔数门（样本 `S==251`，值每构建随机）。
- `[普通帧]` / `[协程帧]` 两套；`UL`：先空 `yield`，再 `yield(true,k,v)` 传表。
- **upvalue cell 布局按样本映射**（F30，对应我方 §8.1 三形态）：
  cell = `{[4]=bank,[7]=slot}`，读写 = `bank[slot]`；
  - Plain（我方 `slot` 形态）→ bank=创建帧寄存器文件、slot=槽；
  - 循环新 cell（我方 `0x8000|slot`）→ `D[4]=D`（自引用银行）+ 值存固定键
    （样本 `[6]`），同迭代闭包共享；
  - 别名（我方 `0xC000|upidx`）→ 直接传父帧 cell 对象；
  - 闭包创建 handler 的 4 种绑定形态（样本 `bv`=0 新建/1 寄存器副本/
    2 复用入参 cell/3 跨银行）与我方描述符三分支一一对应，逐分支写测试。
  这是最容易把 204 矩阵打爆的一步（语义模型换代级风险，同 §8.1 当年）。
- 协程：用户 `coroutine.*` 映射到宿主；跨 yield 多值走 UL。
- **入口函数生成**：makefn 原语放**状态元组槽**（样本 `z[4]`，位置每构建随机），
  经 `b[z[4]](b, proto, b.s, nil)` 调用，`s={}` 空表作环境/暂存传入（F31）。

**验收**：F12 F30 F31；`tests/cases/stress_upvalues.lua` + `stress_coroutines.lua` 在 `--preset v15` 下与原脚本 stdout/exit 一致。

### P7 — 7-bit 拆块 + 自修改 + 不透明算术 + 风格语法（约 3–4 天；§1.1 扩充）

- 逻辑寄存器 = 上下文表里 2–3 个 7-bit 槽，读写都重建；槽位每构建随机；
  **块字节 +128 偏置**，重建用乘加（`*128`/`*16384`/`*2097152`）不用位运算。
- 四个 SoA 银行表共享一个 metatable（样本 10.5）。
- 超级指令：选 8–15 条高频「算术+比较+分支」融合体直接内联进执行树
  （不是独立 handler），配合**融合条件返回** `return not(C)and N or M, ...`
  （样本 113 处）与双重否定/反向比较（`not not(...)`、`not(G>=128)`）。
- **varint 4 级内联阶梯**（样本 [73] 形态）：`u<128`→1B、`S<128`→2B、
  `T<128`→3B、else 4B，嵌套 if 手写展开，不走循环。
- **字节码自修改（F27）**：解码/特化步骤运行期写回 SoA 常量
  （`J[Q]=<新 opcode>`，样本 9 处）——指令流首次执行时自我替换。
- **不透明槽位算术（F29）**：SoA 写回路径套随机常数 mul32 线性变换
  （读侧配对逆变换），常数每构建随机。
- **风格语法**：if 表达式（F22：自动建表 `v=if not v then{}else v` +
  条件选择）、复合赋值（F24：`p+=1` 等，Luau 原生支持）——发射器按
  概率混用；我方解析器侧**不需要**支持 if 表达式输入（只出不进）。

**验收**：F13 F14 F22 F23 F24 F27 F29；反汇编/读源看不到 `V[a+1] = V[b+1] + V[c+1]` 这种直给式。

### P8 — `nL` 错误重写进模块表 + 指纹全绿 + 语料（约 1–2 天）

**验收**：F17 + 全表 F1–F32；v15 档语料绿；旧预设仍 204+405。

## 7. 工作量与风险

| 阶段 | 估时 | 主要风险 |
|---|---|---|
| P0 脚手架 | 1 天 | 指纹写松会假绿；解析口径坑（if 表达式/函数深度）已在 §P0 注明 |
| P1 外壳 | 2–3 天 | 关 L5 后字符串/体积形态大变，minify/mangle 交互 |
| P2 槽/解包 | 1–2 天 | 低；68 原语清单按 §P2 实测表照抄 |
| P3 引导/执行双结构 | 4–5 天 | 状态元组排列与 handler 签名必须同一套 RNG；执行循环内联化的模板复杂度 |
| P4 blob 形态 | 2 天 | 长串 `]=]` 转义；buffer 边界；+128 偏置与解码器一致性 |
| P5 密钥双层 | 1 天 | 诱饵层必须静态不可达但语法完整；真实层常数注入点别漏 |
| P6 CPS 帧 | 3 天 | **upvalue / 协程 / 尾调用**，矩阵最容易红 |
| P7 拆块+自修改+风格 | 3–4 天 | 自修改 × 多段循环的 pc 语义；不透明算术的读写配对逆变换；性能再降一档（样本约 190 万 op/s，可作上限参考） |
| P8 收口 | 1–2 天 | 指纹与语料对打 |

合计大约 **3–4.5 周** 单人（含回归），其中 P3+P6 占一半以上。

**最大风险**：CPS 帧 × 单 cell upvalue。v15 用「每帧新闭包 + `bank[slot]` 活引用」
（cell 布局 `{[4]=bank,[7]=slot}`，循环 cell 自引用银行）绕开了值副本问题；
我们 §8.1 的三种描述符按 §P6 的映射表逐分支落地，不能再 GetUp 拷贝。

**次大风险**（二轮详读新增）：执行循环内联化（P3-B）与自修改（P7）叠加后，
pc/状态语义在「引导管线状态机」与「执行循环指令下标」两套体系间切换，
跳转重定位极易错——建议引导期先用**固定**状态 ID 池打通全链，再上随机面。
