## 0. 威胁模型与防御总纲

Luraph v15 面对的攻击者分三类，其防御按「让攻击成本最大化」设计：

| 攻击者 | 手段 | Luraph 的核心对策 |
|---|---|---|
| **静态逆向** | 读源码/反编译还原逻辑 | 字节码虚拟化 + 数据全入 blob + 分发打散 + 编码混淆 |
| **动态调试** | 运行时 hook/单步/改字节码 | 自修改字节码 + 状态机分发 + 错误行号重写 |
| **通用脱壳器** | 写一次工具批量脱 | **每构建唯一**（常数/槽位/树形全随机） |

**设计哲学**：不追求「密码学不可破」（自包含脚本的密钥必然可恢复），

## A. 载体与数据层防御

### A1. blob 长串数据层（`RC = [=[LPH:...]=]`）

**机制**：全部程序数据（指令流 + 常量池 + 原型树）编码进**单一长字符串**
`RC`，实测 **74 566 字节**，一级长串 `[=[...]=]`，前缀 `LPH:`。文件其余部分
只有分发骨架与少量字面量。

**防御对象**：静态逆向。攻击者面对的是一坨不透明编码数据，而非可读的
Lua 结构；`LPH:` 前缀是解码入口的识别标记（解码时 `string.sub` 剥掉）。

**强度**：高。数据与代码彻底分离，静态工具看不到任何指令/常量形态。
**弱点**：blob 本身是「数据在哪」的明显标志，攻击者知道要解它。

### A2. base-N 编码 + pC/XC token 转义

**机制**：
- `XC = "[ -'}~]"`——解码字符类（ASCII 32..126 的可打印区间，作 Lua pattern）。
- `pC`——**10 条**「单字符 → 5 字符 token」转义表（如 `"` → `=W8+C`、
  `%` → `]JEL>`）。编码时把会破坏载体/触发解析的特殊字符替换成 5 字符
  token；解码时 `string.gsub(s, XC, pC)` 反演。

**防御对象**：静态 + 字符级分析。特殊字符（引号/百分号/空格等）若原样进
载体会破坏长串或暴露结构，token 化后载体是纯「安全字符流」。

**强度**：中。它本身不是密码（可逆、表在文件里），但让载体成为统一的
可打印流，为上层 XOR/解码铺路，并抹掉字符级特征。

### A3. 字符串字面量极简（全文件仅 30 个）

**机制**：整个文件**只有 30 个字符串字面量**——所有程序字符串都封进 blob。
裸露的只是解码必需的少量常量（`LPH:`、`XC`、pC 的键值、错误正则等）。

**防御对象**：字符串搜索定位。攻击者无法靠 `grep` 关键字符串（函数名/
错误消息/常量）定位逻辑——它们全在编码数据里。

**强度**：高（对「靠字符串找线索」的攻击极有效）。
**弱点**：解码骨架本身仍有少量可识别字面量（`LPH:`、正则）。

### A4. Roblox buffer 二进制数据层

**机制**：解码后的数据写入 **Roblox `buffer`**（不透明二进制内存），用
`buffer.create/readu8/writeu8/fromstring` 操作（实测 `buffer.*` 17 处、
`readu8` 245 次、`writeu8` 71 次、`create` 24 次、`fromstring` 2 次）。

**防御对象**：静态 + 半动态。`buffer` 是不透明二进制对象，无法像 Lua
table 那样被 `pairs`/序列化直接窥探；字节级读写必须经 `buffer.*` API。

**强度**：高（数据不透明 + 平台绑定）。
**弱点**：**平台绑定**——`buffer` 是 Roblox 专属，普通 Lua 5.1 / 纯 Luau
跑不了（这是我们选择纯 Lua 载体、放弃 buffer 的原因）。

## B. 密钥与密码防御

### B1. 状态机化 LCG 密钥派生（`[96]`，核心密码防御）

**机制**：密钥流源头是一个**状态机化的线性同余生成器（LCG）**，存为数字槽
`[96]`。实测结构：
```
[96]=function(b,b,b,u,u) return function() local u=5;
  while true do
    if u<=3 then if u<=1 then if u<=0 then
      b[1][4][b[1][7]]=(985577*b[1][4][b[1][7]]+234540221)%268435456;
      b[1][4][b[1][7]]=(639055*b[1][4][b[1][7]]+45488747)%268435456;
      b[1][4][b[1][7]]=(627209*b[1][4][b[1][7]]+257144031)%268435456;
      b[1][4][b[1][7]],u=(1031513*b[1][4][b[1][7]]+219713329)%268435456,6;
    else ...
```
要点：
- **LCG mod 2²⁸**（`%268435456`，实测 34 处），一次调用推进**多步**
  （乘数/增量 985577/639055/627209/1031513… 每组不同，**每构建随机**）。
- 状态存于 `b[1][4][b[1][7]]`——**嵌套数字槽**，不是普通局部变量。
- 整个 PRNG 被**展开成 `while` 状态机**（`u=5` 起始，`u<=3/u<=1/u<=0` 分层），
  常数藏在状态转移体里。
- **参数遮蔽**：`function(b,b,b,u,u)` 同名参数重复，干扰阅读。
- 实测全文件 **33 次** `(M*x+C)%2^28` 转移、**68 次**状态槽写入。

**防御对象**：静态密钥提取。攻击者无法靠「找密钥常量」拿到密钥流——
常数分散在状态机转移里、状态在嵌套槽里运行时推进，**必须真正执行或完整
重建这个状态机**才能得到密钥。

**强度**：高（这是「密钥不可静态提取」的关键）。
**弱点**：动态执行一次即可获得密钥流（自包含脚本的宿命，见 §5）。

### B2. XOR 流密码 + 位置密钥

**机制**：字节级解码用 `bit32.bxor`（实测 91 次调用）做流密码：
`buffer.writeu8(buf, pos, b[8](K0, src[pos], keystream))`，其中 `b[8]=bit32.bxor`，
密钥流 = `(const*pos + const2) % 256`（实测 `(213*M+225)%256`）。
XOR 的常量密钥参数实测为 **18 / 201 / 160**（多个，每构建随机）。

**防御对象**：静态。载体字节不是明文，需密钥流才能还原。

**强度**：中。XOR 流密码本身弱（已知明文可提密钥流），但与 B1 的
「密钥运行时派生」结合后，静态提取成本显著上升。
**弱点**：流密码 + 自包含 → 动态已知明文攻击可提密钥流（根本约束）。

### B3. 多重密钥常数

**机制**：不止一组密钥常数（18/201/160 三组 + 213/225 派生对），不同解码
阶段用不同常数，且全部每构建随机。

**防御对象**：静态 + 通用脱壳。攻击者即便摸清一组，也要逐构建重摸。

## C. 分发与控制流防御

### C1. 三层分发（v15 相对 v14 的核心演进）

**机制**（实测数字）：
- **146 个 `=function(`、141 个不重复具名函数**。
- **351 处 `return <数字>,` 状态返回、136 个独立状态 ID**。
- **727 处方法调用**，热路径是算术助手 `iL`(330)/`vL`(239)。
- 结构：顶层 `FC`/`L` `while` 状态机 → 子分发器 → 141 个细粒度 handler。
  每个 handler 吃状态元组、做一小步、`return <下一状态>, <元组>`。

**防御对象**：静态控制流重建。没有单一巨型分发函数可定位——
opcode→动作映射散落在上百个函数里，静态分析必须跨函数重建完整状态图。

**强度**：高。这是「找不到分发中心」的关键。
**弱点**：动态收敛点（子分发器入口）仍可 hook（见 §5）。

### C2. 状态元组位置传参

**机制**：执行状态打包成位置参数元组在函数间传递，元组里**混入函数引用**
（原语指针走参数而非全局名），进一步隐藏「哪个函数是解密器」。

**防御对象**：静态数据流分析。状态无固定全局载体，难以追踪。

### C3. continue 扁平叶（实测 45 处）

**机制**：分发树的叶子形如 `状态 = b:handler(...); continue`——扁平
分支 + `continue`，避免深嵌套 `else` 链，改变静态树形态、降低可预测性。

### C4. 算术助手热调用（`iL` 330 / `vL` 239）

**机制**：大量调用两个算术助手 `iL`（mul32，用 bit32 组合 32 位乘法）、
`vL`（`%4294967296` 归一）。高频调用把「地址/偏移计算」也卷进混淆网络。

**防御对象**：静态。连索引/偏移计算都不直给。

## D. 指令与操作数编码防御

### D1. 7-bit 分块寄存器编码（实测 264 处 `-128` 偏置）

**机制**：逻辑寄存器/操作数值**拆成 7-bit 块**，分散存放，用时按 128 进制
重建（`*128`/`*16384`/`*2097152` 实测 74/38/24 次），并带 `-128` 偏置
（264 次）、`2^32` 归一（13 处 `%4294967296`）、`bit32.lshift/rshift` 位重建。

**防御对象**：静态寄存器/操作数模式匹配。反编译器无法把「一段连续内存 =
一个寄存器值」，单点 patch/断点无法定位逻辑寄存器。

**强度**：高（对自动化寄存器恢复极有效）。

### D2. 每构建 opcode 置换

**机制**：opcode → 线编码的映射表每构建随机置换（配合死指令填充）。

**防御对象**：通用脱壳器。每次构建的 opcode 编码不同，脱壳工具必须逐构建
重标定。

### D3. 超级指令（实测 ~125 个融合 handler）

**机制**：单个 handler 融合「算术 + 比较 + 条件分支」（本次启发式统计到
约 125 个这类融合体），操作数编码在数据里而非指令里。

**防御对象**：静态指令识别。「一条指令 = 一个语义动作」的假设被打破。

### D4. 自修改字节码（实测 8 处）

**机制**：执行期写回 opcode 数组常量——实测 `J[Q]=12`、`J[Q]=197`、
`J[Q]=58`、`J[Q]=100`、`y[Q]=162`、`y[Q]=3`、`R[Q]=134`、`R[Q]=32`。
即字节码在运行中**改写自身**（首次执行解码/特化，后续执行改后的指令）。

**防御对象**：动态调试 + 静态快照。静态抓到的字节码不是最终执行的形态；
调试器断在某指令，下一次它可能已被改写。

**强度**：中高（对「dump 一次字节码就完事」的攻击很有效）。
**注**：这是我们已吸收并实现的防御（增量 3/4 的字面量自修改即源于此）。

## E. 执行模型防御

### E1. 字节码虚拟化（核心护城河）

**机制**：源码 → Luraph 自定义字节码 → 嵌入脚本的 Lua 解释器执行。
标准反编译器只认原生 5.1/Luau 字节码，对自定义指令**完全无效**。

**防御对象**：标准反编译器。这是整个体系的根基。

### E2. CPS 帧模型（每帧一个 Lua 闭包）

**机制**：每次「函数调用」返回一个新 Lua 闭包（新帧），由宿主协程驱动
（实测 8 处 `coroutine.*`）。帧 = 独立闭包栈帧，调用关系不在单一循环可见。

**防御对象**：动态调用栈分析。调用链被打散成闭包链 + 协程。

### E3. 数字槽原语表（实测 77 个非函数槽，范围 0..126）

**机制**：所有宿主原语（`buffer.*`/`bit32.*`/`string.*`/`coroutine.*`/
`typeof`/`setfenv`…）经**数字槽别名**访问（`b[8]=bit32.bxor` 等），数字槽
每构建随机分配。另有 4 个数字槽函数字段 `[18,63,73,96]`（帧运行器 +
两个 LCG）。

**防御对象**：静态。真实 API 名被数字槽隐藏（全文件裸 `buffer.` 仅 17 处、
`bit32.` 7 处，且几乎都在模块表初始化）。

## F. 错误与反调试防御

### F1. 错误行号重写（`nL`）

**机制**：`nL` handler 是错误重写状态机——捕获未处理错误，用正则
`:(%d+)[:\13\10]`（存于 `gL` 字段）提取报错行号，加随机偏移重映射后
`error(msg, 0)` 重抛。实测引用 `b.EL`/`b[16]=error`/`b.PL`/`b.dL`/
`b[84]=type`/`b.cL`/`b[67]=string.match`/`b.gL`。

**防御对象**：反调试/报错定位。攻击者无法从报错信息拿到真实源码行号/
结构线索。

**强度**：中（低成本高收益的辅助防御）。

### F2 / F3. 缺失：时间陷阱与显式校验和（弱点）

实测 `os.clock` / `os.time` **0 处**、显式校验和 **0 处**、
`loadstring`/`load` **0 处**：
- **无时间陷阱** → 单步调试/动态 hook 不会被「超时自毁」阻断。
- **无显式完整性校验和** → 篡改字节码不一定触发可检测的完整性失败
  （靠自修改间接提高篡改难度，但无主动校验）。

这是样本的**真实弱点**，也是**我们的差异化机会**（我们已实现校验和 +
验证陷阱 + 金丝雀 + 时间陷阱，见 `obfuscation-research.md` L7）。

## G. 每构建唯一性

### G1. 全构建随机化

**机制**：每构建随机化的维度——数字槽分配、所有密码常数（LCG 乘数/增量、
XOR 常数）、字符 token、派发树形、分块方式、状态元组序、命名。

**防御对象**：通用脱壳器。**这是商业混淆器的根本壁垒**：攻击者写的工具
只对「这一个构建」有效，下一个构建全部失效，必须重写。

**强度**：极高（成本防御的核心）。

## 4. 防御协同（体系视角）

各防御不是孤立的，而是层层嵌套、互相放大：

```
静态攻击者看到的：
  一坨不透明 blob (A1/A4)
  └─ 想解它 → 需要密钥流 → 密钥在状态机 LCG 里 (B1) → 必须执行/重建状态机
  └─ 想读骨架 → 141 个打散的 handler (C1) → 无法定位分发中心
  └─ 想匹配寄存器 → 7-bit 分块 (D1) → 模式匹配失效
  └─ 想脱壳 → 每构建唯一 (G1) → 工具一次性作废

动态攻击者看到的：
  字节码运行中自修改 (D4) → dump 的不是最终形态
  帧 = 闭包链 + 协程 (E2) → 调用栈打散
  报错行号被重写 (F1) → 拿不到定位
  ⚠ 但无时间陷阱 (F2) → 单步调试不被阻断 ← 突破口
```

**协同要点**：
1. **数据层（A）+ 密码（B）**：blob 给你数据，但解它要密钥；密钥在运行时
   状态机里。二者相乘。
2. **控制流（C）+ 指令编码（D）**：即使拿到字节码，分发的打散 + 操作数的
   分块让重建语义仍然昂贵。
3. **每构建唯一（G）放大一切**：上述所有静态/动态工作，每个构建都要重来。

## 5. 诚实评估：弱点与可破解点

按可利用性排序（攻击者视角）：

1. **动态收敛点 hook（最有效）**：子分发器入口 / 执行循环的 `pc` 推进点是
   收敛的，hook 这些点记录 `(状态, 数据变化)` 序列即可离线重建语义。
   **无时间陷阱**意味着这条路不被阻断。→ 样本最大软肋。
2. **动态执行一次提密钥流**：自包含脚本的宿命——跑一遍就有密钥流
   （已知明文攻击对流密码一击致命）。
3. **无完整性校验**：篡改字节码无主动检测（只有自修改的间接干扰）。
4. **平台绑定**：`buffer` 依赖使其只能在 Roblox/特定 Luau 环境跑
   （对攻击者是限制，对移植也是限制）。

**结论**：v15 的防护强在**静态**与**每构建唯一**，弱在**动态抗调试**
（无时间陷阱、无显式完整性）。它的壁垒本质是「成本」，不是「不可破」。

## 6. 对我们实现的启示（对照与采纳）

| 样本防御 | 我们的现状 | 决策 |
|---|---|---|
| E1 字节码虚拟化 | ✅ 已实现（核心） | 保持 |
| G1 每构建唯一 | ✅ 种子驱动全随机 | 保持 |
| D4 自修改字节码 | ✅ 增量 3/4 已实现 | 保持 |
| B1 状态机化 LCG 密钥 | ✅ 安全增量 S1 已实现（KSC+KG 槽） | 保持 |
| A3 字符串极简 | ✅ L2 全量字符串加密 | 保持 |
| F2/F3 时间陷阱+校验和 | ✅ **我们超样本**（antidbg L7） | 保持（差异化） |
| A1/A2 blob 长串 + base-N | ⬜ P4 阶段待做 | 计划中 |
| D1 7-bit 分块 | 🟡 有 varint，未做分块不透明化 | **S2 安全项** |
| C1 三层分发 + C2 元组 | 🟡 已有 CPS 骨架，未全量 | 阶段 C |
| D3 超级指令 | ⬜ 未做 | 阶段 C/后续 |
| E2 CPS 帧 | ⬜ 未做 | 阶段 D |
| A4 buffer 数据层 | ❌ 拒绝（破坏 5.1 兼容） | 拒绝（纯 Lua 载体） |

**差异化优势**：样本缺的**时间陷阱 + 显式校验和 + 金丝雀**我们都有
（`antidbg.rs` L7），这是我们对样本的**净安全优势**，必须保持。

**最该补的安全差距**（按优先级）：
1. **D1 → S2**：操作数 7-bit 分块不透明化（纯安全，中等风险）。
2. **C1/C2/E2 → 阶段 C/D**：执行 CPS 化 + 每帧闭包，抬高动态分析成本
   （安全 + 结构双收益，高风险）。
3. **A1/A2 → P4**：blob 长串 + base-N + token（结构 + 部分安全）。

> 底线不变：自包含脚本密钥必然可恢复，壁垒是「每构建唯一 + 提取成本」。
> 我们的路线 = 守住已有优势（反篡改/时间陷阱），补齐样本的编码与分发
> 强度，拒绝破坏双目标兼容的手段（buffer）。
